# 2026-09-21 to 2026-09-23: the tool started measuring itself

The geofence fired unattended on a real commute for the first time, which
turned the open question from "does the phone work" into "was the advice any
good". Answering that needed arrivals recorded, so this session built the
collection side, fixed the rate limit that had been quietly eating the events
signal, and dragged production up to date — it had been four days behind and
was missing a whole signal without anyone noticing.

Released as 1.3.0. 320 tests pass. Cloud Run revision `switchtender-00013-wsc`.

## What changed and why

- **The phone works, and it is now written down (PR #19).** The 2026-09-21
  drive fired at the trigger point at speed, the call returned, and the
  verdict was spoken with road left to act on it. That closed the last open
  step in `docs/phone.md`, which had told a future reader to widen the radius
  or move the pin if it fired late. Neither was needed: 400 m at
  `lead_miles = 4.0` is confirmed in the field, not reasoned from the Play
  services fix interval.

- **Ticketmaster venue ids live in config now (CMB-42, PR #20).** The vendor's
  public quota is **2 requests a second**, not the 5 usually assumed, and
  `fetchTicketmaster` re-resolved every venue name to a vendor id on every
  run: three resolve calls plus the events call, back to back, which is over
  the limit whenever the vendor answers quickly. Two rows in 42 had come back
  `venue lookup HTTP 429`, one of them on a real drive. A `[[venues]]` entry
  now takes an optional `ticketmaster_venue_id` and skips its lookup; a venue
  without one still resolves and the run prints the id it found, so adding a
  venue needs no lookup step. Measured live: 4 requests a run before, 1 after,
  the same events found.

- **A failed venue lookup no longer discards the venues that answered.** It
  used to return `events: null` on the first error. Now the venue that failed
  goes to `unresolved` with its reason in the assessment's notes, the answer
  is marked `partial`, and a zero from the rest still reads as unknown
  (rule 4).

- **A 429 is retried once**, honouring `Retry-After` when it is a count of
  seconds, capped at 2 s and bounded by the existing deadline. Nothing else is
  retried. This needed `src/http.js` to report `status` and `retryAfter`
  beside the message; it still never carries the URL, and so never the key.

- **`POST /arrived` (CMB-41, PR #22).** `?place=park|office`, same
  `X-Switchtender-Key` header, `&at=<ISO 8601>` for a request the phone queued
  offline. It appends to a separate `arrivals` tab holding `timestamp`,
  `local_date`, `weekday`, `place`, `verdict_timestamp`, `source`. A separate
  tab rather than a column written back into the verdict row, because the
  verdict is appended at the fork and the arrival lands minutes later on an
  instance that no longer exists — the row index from that append is gone. A
  repeat arrival for the same place on the same local date is ignored: a Play
  services geofence can fire twice on one approach, and a lunch trip re-enters
  the office fence. It answers 200 whenever the request itself was sound,
  including when the sheet write failed, because a retryable status would only
  make the macro queue duplicates.

- **`&took=drive|transit` and a `choice_taken` column (CMB-41, PR #23).** Added
  hours after the endpoint, because the first real arrival row could only be
  scored from something the owner said in conversation. The schema knew what
  was advised and not what was done, and the advice can be ignored. Absent is
  null, never a default; a guessed option would look like evidence. The column
  is appended at the end of `ARRIVALS_HEADER` so the live tab's header extends
  in place, the same discipline `EXTRA_COLUMNS` follows.

- **The deploy script could not re-key the scheduler (PR #24).** `gcloud
  scheduler jobs update http` takes `--update-headers`; `--headers` is
  create-only. Every redeploy after the job first existed failed at that step,
  so the job's URI, schedule and header were unupdatable — and gcloud echoes
  every argument on a parse error, which put the shared secret in the deploy
  output. Fixing the flag removed both problems.

## Production was four days stale, and it cost a signal

Revision `switchtender-00010-l76` was deployed 2026-09-18T14:40Z. The WMATA
rail-alert commit landed at 15:04Z the same day, 24 minutes later. So CMB-35
had never run outside a laptop: every live verdict since, including both real
drives, was decided with no rail-alert signal, and the sheet's four `wmata_*`
columns were neither labelled nor written.

The first `/verdict` from the new build extended the header in place from 60
to 64 columns and wrote `wmata_active = 0`. Later the same day a call came
back `wmata_active = 1` — a live alert scored in production for the first
time.

The lesson is not about WMATA. Landing on `main` changes nothing here until
someone deploys, and nothing in CI or the repo says how far behind production
is. Check the revision date against `git log` before concluding a signal is
broken.

## The shared secret was rotated

The old value had been printed by the scheduler argument error, and any deploy
log since the job existed holds it. `scripts/deploy-cloud-run.sh
--rotate-secret` minted a new one: Secret Manager version 3, the previous
1Password item archived rather than edited (`op item edit` takes field values
as arguments, which would put the secret in argv). The old key now returns 401
and the new one 200. The scheduler took the new header and a forced run
returned HTTP 200 — which only worked because of PR #24. **Order matters for
any future rotation: fix the scheduler path first, rotate second, then update
every macro.** Rotating while the update path is broken leaves a job
authenticating with a dead key and a weekday push that fails silently.

The MacroDroid fork macro was re-keyed by the owner the same evening.

## Where the measurement stands

Two scored data points, which is not history and does not satisfy rule 3.

- **2026-09-21 08:49** — drive, 43 against 76. No arrival recorded; the
  capture did not exist yet.
- **2026-09-22 08:28** — transit, 69 against 75, margin 6.3 against a required
  10.8. The owner took the train and reached the office at 09:34:31 against a
  predicted 09:43:33: **9.0 minutes early**, transit running about 66 minutes
  against 75 predicted, roughly 12 % pessimistic on that one trip. Whether the
  drive estimate was equally pessimistic is unknowable; the counterfactual was
  not run. That row was written through `logArrival` from a laptop, so its
  `source` is `manual` and its `choice_taken` was backfilled by hand on the
  owner's word.

**The trap in scoring these.** `drive_arrival` and `transit_arrival` have been
columns since 2026-09-17 and are populated on every row — they sit past column
AZ, which is how an earlier read of the sheet missed them. Both are computed
as the moment of the call plus the option total, and with `measured_from =
fork` the call happens four miles *before* the fork while the total covers
only the leg *after* it. So both predictions are short by the unmeasured
run-up, and a trip that beats them beats them by more than the raw delta says.
Score with that in mind, or call with `?from=origin`.

## Not changed, by choice

- **No request pacer**, though CMB-42 asked for one. With the ids configured
  there is one Ticketmaster request a run, so a pacer would gate a single call
  for the cost of either real sleeps in the test suite or an injected clock
  threaded through `fetchEvents`. The one path that still makes several calls
  — a venue added without an id — is covered by the retry. Worth revisiting
  only if a 429 appears again.
- **The two logged drives were not backfilled with arrivals.** Neither has a
  recorded arrival time and guessing one would poison the first rows of the
  sample.
- **`docs/switchtender.macro` still holds only the fork macro.** The arrival
  macros are documented but not exported; that wants a device round-trip.
